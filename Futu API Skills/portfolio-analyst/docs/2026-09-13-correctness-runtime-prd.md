# Portfolio Analyst 分析正确性与运行验收 PRD

日期：2026-09-13\
状态：用户已于 2026-09-13 确认；按该范围实施，验收结果另见同目录验收记录。

## 1. 目标与问题

让用户在当前美股、USD 账户分析中获得口径正确、缺失证据明确、运行状态可诊断的报告。

本轮代码检查已经复现两个分析问题：

- 分类未知的持仓被合并到 UNKNOWN 桶，然后作为同一真实行业、地区或题材触发集中度超限。
- 有效持仓数直接取 NAV 权重平方和的倒数；一只股票占 10%、现金占 90% 时显示 100，不能表示股票持仓的实际分散程度。

另外，运行环境存在多个解释器，诊断把 SDK 导入与 OpenD 握手放在同一超时中，容易把连接失败描述为 SDK 未验证。测试数量和实际可用性需要分别报告。

## 3. 范围选择

可选方案：

1. 只修两个指标：范围最小，但运行入口与验收证据仍不清楚。
2. 修指标、明确运行环境、补齐诊断与验收：本 PRD 推荐范围。
3. 同时建设画像、分类数据服务与绩效数据链：产品能力更广，但依赖与验收明显扩大，应另写 PRD。

本轮已确认采用方案 2。行业分类服务、用户画像与历史绩效扩展进入后续需求，避免基础口径问题被扩展工作掩盖。

## 4. 用户故事

1. 作为用户，我希望分类缺失明确显示为未知，避免被告知一个没有证据的行业超限。
2. 作为用户，我希望即使部分分类缺失，已经有证据证明的集中风险仍能被识别。
3. 作为用户，我希望现金比例变化不会把一只股票变成几十个“有效持仓”。
4. 作为用户，我希望报告保留账户 NAV 权重，能将分散程度和资金投入比例分别理解。
5. 作为用户，我希望运行诊断明确区分 SDK 未安装、导入失败、OpenD 不可达和握手失败。
6. 作为维护者，我希望按项目指定解释器重现实测结果，明确平台差异与环境限制。
7. 作为维护者，我希望历史报告仍可按原版本读取，当前报告使用的新口径可追溯。
8. 作为用户，我希望真实连接或模型评测未完成时明确说明，不能用单元测试通过代替。

## 5. 功能需求与验收标准

### P0-A：分类缺失与集中风险分开计算

保留 UNKNOWN 在完整暴露表中的占比，但不得将其作为一个已知行业、地区或题材判定集中风险。

每个分类维度应独立输出已分类权重、未知权重、判断依据，以及约束状态：BREACHED、WITHIN_LIMIT、UNKNOWN 或 NOT_CONFIGURED。

- 已知某个分类的权重已经超过用户上限时，即使其他持仓未知，仍可确认 BREACHED。
- 已知分类没有超限，但未知部分可能使某个分类超限时，状态为 UNKNOWN，不能报告通过。
- 只有在包含未知部分的保守上界也不超过上限时，才可确认 WITHIN_LIMIT。
- 没有配置个人上限时为 NOT_CONFIGURED；数据覆盖和已知暴露仍应展示。
- 题材约束使用原有 split 口径；full 视图保持重叠展示用途。未知题材份额的上下界计算需要遵守同一 split 口径。
- 默认“三项主要风险”的输出不得为凑足数量制造风险；可明确呈现证据缺口或暂无可确认风险，不能建议降低 UNKNOWN 行业仓位。

验收样例：

| 输入 | 预期 |
|---|---|
| 股票合计 90%，分类全部未知，上限 60% | 未知 90%；约束 UNKNOWN；不生成 UNKNOWN 行业／地区／题材 HIGH 集中度结论 |
| 已知科技 70%，未知 20%，上限 60% | 科技 BREACHED，同时披露未知 20% |
| 已知科技 40%，未知 30%，上限 60% | UNKNOWN；不得报告上限已满足 |
| 已知科技 30%、医疗 20%、未知 10%，上限 60% | 保守上界 40%，WITHIN_LIMIT；仍披露未知 10% |
| 无分类上限 | NOT_CONFIGURED；不隐式添加个人风险阈值 |

### P0-B：明确有效持仓数的分母

保持 NAV、现金权重、单股 NAV 权重和 Top 1/3/5 权重原有口径，禁止为了指标方便改写账户估值或强制持仓权重合计 100%。

针对受支持的非负经济持仓，令 `L = sum(w_i)`，其中 `w_i` 为 NAV 权重：

- 原 NAV 权重平方和可保留，但必须标明口径。
- 持仓内部 HHI 使用 `sum((w_i / L)^2)`。
- 持仓内部有效持仓数使用 `L^2 / sum(w_i^2)`。
- 合并同一证券的跨账户记录后计算，保持已有身份与元数据校验。
- `L = 0` 时有效持仓数为未知／不适用，不能生成无穷大或虚构持仓数。
- 多空组合保持当前明确不支持的边界，不在本轮引入未经设计的净额或绝对值替代。

验收样例：

| 输入 | 预期 |
|---|---|
| 一只股票 10%，现金 90% | 有效持仓数 1；股票 NAV 权重仍为 10% |
| 两只股票各 25%，现金 50% | 有效持仓数 2 |
| 两只股票的相对比例保持一致，只改变现金占比 | 持仓内部有效持仓数不变 |
| 全部现金，没有受支持持仓 | 有效持仓数不适用 |

### P1-A：运行入口和诊断可区分

文档明确运行环境和测试环境的职责，所有验收记录显示实际解释器路径与版本。

- 当前真实 CLI 运行使用仓库根 `.venv/bin/python`；不通过裸 `python` 假设解释器。
- SDK 的安装状态、导入状态、版本、必要接口可用性应单独记录。
- OpenD 可达性和 API 握手使用独立、有上限的诊断阶段。导入已经成功时，握手超时不得覆盖 SDK 成功事实。
- 权限导致的日志写入失败、ModuleNotFoundError、连接拒绝和握手超时应有不同诊断原因。
- 自动化测试可不安装 SDK，但真实集成验收必须使用已验证 SDK 的解释器。
- 不自动切换到系统解释器、修改全局环境或重复安装已有依赖。
- 诊断仅使用只读行情能力，不解锁交易或查询交易密码。

验收：已安装且可导入 SDK、OpenD 未运行时，结果明确表现为 SDK 可用、OpenD 连接不可用；总状态可失败，但不得显示 SDK 未安装。

### P1-B：平台测试与真实链路验收

- 排查 macOS `/tmp` 解析差异，明确稳定错误码契约。
- 排查两项子进程清理测试，区分仍在执行、已退出但尚未回收，以及平台探测能力差异。不能仅删除断言或无理由跳过测试来获得通过。
- 排查日志并发写入的不稳定结果，验证并发写入记录完整、无丢失、哈希链一致；记录解释器与平台条件。
- 在受支持的 macOS 与 Linux 环境分别报告测试结果；单个平台未执行必须标明未验证。
- OpenD 可用且用户账户范围明确后，使用根环境运行 doctor 和一次只读当前分析，检查 snapshot、risk、technical、条件 options 的绑定及局部降级。
- 股票／ETF、空仓、分类未知、持有期权、非支持空头及依赖失败使用合成数据覆盖；真实账户只验证实际存在的持仓类型。
- 无可用 OpenD 或账户范围时，集成验收保持“未通过／未执行”，不得以合成结果替代。
- 至少运行一次仓库现有真实模型合成评测，保留独立执行证据；报告路由和覆盖结果与人工审查的语义质量分开记录。

## 6. 设计与兼容性要求

- 将“分类覆盖及约束判断”和“持仓内部集中度”作为可独立验证的计算单元。
- 风险报告生产、语义验证、报告展示和模拟中使用一致的口径；检查绩效等下游使用点，避免出现新旧定义混用。
- 新指标含义与分类约束状态必须有报告版本标识。旧保存报告按旧版本验证，展示旧口径；不得把新公式静默套到旧结果。
- 证据不足时的中间状态必须进入结构化结果，不能只靠模型在文字里补一句免责声明。
- 模型报告必须消费新的分类覆盖和约束状态；不把 UNKNOWN 重新叙述为确认超限。
- 保留快照身份、来源时间、只读边界、局部降级与默认不持久化的现有约束。

## 7. 验证方法

测试优先覆盖外部行为和经济含义。上述验收样例的预期值由独立简单算例确定，不允许测试通过调用生产算法得到“期望答案”。

覆盖未知分类、部分已知分类、全部已知分类、阈值边界、现金比例变化、跨账户同证券汇总、空仓、精度、旧版报告与下游展示。

分别记录：确定性计算测试、平台及进程测试、SDK/OpenD 集成、真实模型合成评测、人工报告质量审查。任一结果不能代替其他层的通过。

## 8. 本轮不包含

- 用户画像 `--profile-dir`：另行定义规则优先级、有效字段与冲突处理。
- 自动行业／题材分类服务：本轮处理缺失分类的正确性，后续建立带来源和更新时间的分类数据。
- 四季度基本面和估值结构化采集、候选股票比较。
- 资金流水、公司行动、完整历史 TWR／IRR 数据链。
- 多空风险模型、ETF 穿透、期权组合压力测试及交易执行。
- 与上述问题无关的大规模重构。
